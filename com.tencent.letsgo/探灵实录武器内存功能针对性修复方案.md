# 探灵实录武器内存功能针对性修复方案

## 1. 文档目的

本文针对当前 `MemoryLetGoHacker.cpp` 中“探灵实录”相关武器、近战范围和道具功能失效或不稳定的问题，给出以对象类型恢复、内存访问安全和可验证性为核心的修复方案。

本文不把“字段能在客户端写入”等同于“服务器认可其结果”，也不讨论反作弊绕过。所有写入效果应只在获得授权的本地、离线或测试环境中验证；线上环境优先保留只读诊断能力。

## 2. 当前结论

当前实现不能通过继续调整倍率或增加写入频率修好。主要问题位于更前面的对象定位与生命周期管理：

1. `ChestPVE` 角色使用了错误的库存组件偏移。
2. 获取到指针后没有验证运行时类及继承关系。
3. 切换武器时把旧快照恢复到了新武器对象。
4. 多个 1 字节 `bool` 字段被按 4 字节整数写入。
5. 道具功能通过类名包含 `Prop` 扫描全世界 Actor，匹配范围远大于目标类型。
6. 原始值使用 `0` 作为“未捕获”标志，无法正确保存合法的零值。
7. 文档把 `ChestPVE`、`NR3E` 和通用 `MoeFPSBase.Weapon` 的证据混在一起，部分“低风险、客户端权威”结论没有证据支持。

因此，修复优先级必须是：

```text
模式识别 -> 对象类型确认 -> 正确对象链 -> 类型化读写
        -> 按对象保存快照 -> 可逆恢复 -> 只读验证 -> 功能验证
```

### 2.1 2026-08-06 第一轮处理状态

本轮采用“先停止错误写入，再基于证据重建”的处理方式。尚未具备运行时类型验证、按对象快照和字节级读写基础设施，因此没有把错误路径替换成另一套未经验证的写入，而是从可执行源码中完整删除：

- 错误的 `self+0xAB8 -> inventory+0xC8` 武器入口及全部武器增强实现。
- 快速射击、弹药、伤害、换弹、射程、近战、多重倍击、AOE、锁定、持武不减速、无后座力和聚点相关状态、声明、UI、恢复与 Tick 调用。
- 通过类名包含 `Prop` / `Damage` 进入固定偏移写入的道具扫描和电锯增强实现。
- 切枪时调用无参数恢复函数的错误生命周期逻辑。

性能方面已同步删除：

- 每 `0.3` 秒获取角色、库存和当前武器并重复应用多组写入的轮询。
- 每 `1` 秒触发道具功能、并周期性遍历 `PersistentLevel->Actors`、解析类名和 Effect 的路径。
- 已关闭功能仍参与全局恢复和切枪恢复的无效调用。

本轮保留怪物控制、战斗防御、移动、钓鱼和星世界等与上述错误路径无关的现有模块。后续如要恢复武器或特定道具能力，必须从本文 P1 只读探针开始，不得复制已删除实现。

验证结果：全量 NDK 构建已完成所有 C++ 编译、可执行文件链接和安装，产物位于 `元梦绘制泪心核心收费源码/libs/arm64-v8a/letgo.sh`。构建日志没有 C++ 或链接错误；Windows 下的 NDK `make` 对中文文件名 `综合内核全驱动对接泪心整合适配版.h` 执行 `stat` 时报告 `Illegal byte sequence`，导致命令最终返回非零状态。该问题属于现有中文路径/工具链兼容性，不是本轮源码错误。

### 4.2 已确认禁止继续沿用的错误方向

以下做法已经证明会产生错误对象、错误布局或不可恢复状态，不应继续通过调倍率、加写入频率或放宽数值范围来尝试：

1. 不识别角色类，所有模式统一使用 `self+0xAB8`。
2. 只凭“地址像指针”就把对象当作 `AWeapon`。
3. 只凭类名含 `Prop` 或 `Damage` 就套用固定子类偏移。
4. 用 `写入整数` 处理 native bool 和 `uint8`。
5. 用一组全局原始值同时服务多把武器。
6. 恢复时重新获取当前对象，而不是恢复快照所属对象。
7. 用零值作为是否捕获的状态标志。
8. 把道具恢复挂到武器切换流程。
9. 把无 `Net` 标记直接解释为客户端权威。
10. 把 `Net/RepNotify` 字段在客户端可改直接解释为服务器会接受。
11. 把 DataAsset 非复制直接解释为最终游戏结果可由客户端决定。
12. 在未确认精确运行时类名之前硬编码所谓电锯类名。

### 4.3 错误的 ChestPVE 武器入口

当前代码：

```text
self + 0xAB8 -> inventory + 0xC8 -> weapon
```

ChestPVE 修复后的候选链应为：

```text
AChestPVEGameCharacter
  + 0xA98 -> UMoeCharInventoryComponent
  + 0x0C8 -> AWeaponBase
```

这条链仍然必须通过运行时类名和继承关系确认，不能只靠地址范围判断。

### 4.4 切枪恢复写错对象

当前流程：

```text
发现 currentWeapon != lastWeaponPtr
  -> RestoreAllWeaponHacks()
  -> 每个 Restore 函数再次调用 GetCurrentWeapon()
  -> 得到 currentWeapon
  -> 把 lastWeaponPtr 的原值写入 currentWeapon
```

修复要求：

- 所有恢复函数必须接收明确的目标地址。
- 快照必须记录它属于哪个对象。
- 切枪时先对 `lastWeaponPtr` 执行恢复，再捕获 `currentWeapon`。
- 如果旧对象身份校验失败，只丢弃快照，不向未知或复用地址写回。

推荐接口：

```cpp
bool CaptureWeaponSnapshot(uintptr_t weapon, WeaponSnapshot& out);
bool RestoreWeaponSnapshot(const WeaponSnapshot& snapshot);
void ClearWeaponSnapshot(WeaponSnapshot& snapshot);
```

禁止在 `RestoreWeaponSnapshot()` 内重新调用 `GetCurrentWeapon()`。

### 4.5 bool 被按 int32 写入

`写入整数()` 明确通过 `write<int>` 或 `sizeof(int)` 写入 4 字节。以下调用必须改为 1 字节写入：

- `weapon + 0x49E`
- `weapon + 0x584`
- `weapon + 0x508`
- 其他 SDK 标记为 1 字节 `bool` 的地址

应在底层内存接口增加：

```cpp
bool 写入字节(uintptr_t addr, uint8_t value);
bool 读取字节(uintptr_t addr, uint8_t& value);
```

对于真正的位域，必须先读取包含位域的原始字节或整数，再用掩码只修改目标位。不能把普通 `bool`、位域和 `int32` 使用同一个接口。

### 4.6 原始值状态不完整

当前实现大量使用以下方式判断是否已经捕获：

```cpp
if (original == 0) {
    original = current;
}
```

合法原始值本身可能为 `0`，例如空弹夹、关闭状态、无减速、零耗能。应为每个字段增加独立的捕获状态：

```cpp
template <typename T>
struct CapturedValue {
    bool captured = false;
    T value{};
};
```

快照不能依赖正数、非零或特殊浮点数作为状态标志。

### 4.7 多重判定的原始 bool 捕获顺序错误

`ApplyMultiHit()` 先记录 `g_OriginalCheckDamageInterval`，随后又以其是否小于等于零决定是否捕获 `bAlwaysCheckDamage`。正常情况下前一步已经把它设为正数，导致原始 bool 不会被记录，恢复时默认写回 `false`。

这部分应由一次性的完整快照统一捕获，禁止每个字段用彼此的状态作为捕获条件。

### 4.8 道具扫描范围错误

当前 `FindAllProps()` 使用：

```text
className contains "Prop" and not contains "Fishing"
```

随后直接按 `AMoePropActorBase` 布局访问 `0xC34`、`0xC8C`、`0x1040` 和 `0x1274`。类名包含 `Prop` 不能证明对象继承 `AMoePropActorBase`，也不能证明对象实例大小覆盖这些偏移。

必须删除该模糊匹配作为写入入口。正确方向是：

1. 从本地角色的道具管理组件定位当前持有或当前激活的道具。
2. 确认对象继承 `AMoePropActorBase` 或更具体的目标子类。
3. 校验道具所有者确实为本地角色。
4. 读取并记录 `PropTypeId`、运行时类名和实例名。
5. 只有进入经过确认的精确白名单后，才允许进入测试写入路径。

现有静态对象表未找到 `BP_ChestPVE_SupplyProp_ChainSaw_C`。该名称只能作为运行时待确认候选，不能硬编码为已证实类名。

## 5. 建议的代码结构

### 5.1 模式与类型上下文

新增统一上下文，避免每个功能自行猜测对象布局：

```cpp
enum class GameDomain {
    Unknown,
    ChestPVE,
    NR3E,
    MoeFPS
};

struct RuntimeContext {
    GameDomain domain = GameDomain::Unknown;
    uintptr_t self = 0;
    uintptr_t inventory = 0;
    uintptr_t weapon = 0;
    uintptr_t currentProp = 0;
    std::string selfClass;
    std::string inventoryClass;
    std::string weaponClass;
    std::string propClass;
};
```

每次上下文刷新按以下顺序执行：

1. 获取本地 Pawn。
2. 解析 Pawn 运行时类。
3. 根据明确类名选择候选布局。
4. 解析库存组件类型。
5. 解析装备对象类型。
6. 对所有失败原因给出可见诊断信息。

未知模式、未知角色类或类型不匹配时，所有写入功能必须保持关闭。

### 5.2 对象身份

仅比较地址不足以判断对象仍是原对象。至少记录：

```cpp
struct ObjectIdentity {
    uintptr_t address = 0;
    uintptr_t classAddress = 0;
    int32_t internalIndex = 0;
    int32_t nameIndex = 0;
};
```

恢复前重新读取并比较身份。任一项不一致时，认为对象已销毁或地址被复用，禁止恢复写入。

### 5.3 武器快照

推荐把所有武器原始值集中保存：

```cpp
struct WeaponSnapshot {
    bool valid = false;
    ObjectIdentity identity;
    CapturedValue<uint8_t> continuousFire;
    CapturedValue<uint8_t> alwaysCheckDamage;
    CapturedValue<uint8_t> enableSpeedDec;
    CapturedValue<int32_t> clipAmmo;
    CapturedValue<int32_t> carriedAmmo;
    CapturedValue<int32_t> shotCost;
    CapturedValue<float> fireInterval;
    CapturedValue<float> checkDamageInterval;
    CapturedValue<float> weaponRange;
    CapturedValue<float> detectRadius;
    CapturedValue<float> attackExtentX;
    CapturedValue<float> attackExtentY;
    CapturedValue<float> attackExtentZ;
};
```

一个快照只属于一个武器对象。切枪、死亡、重生、返回大厅和模块基址变化时都需要结束当前快照生命周期。

### 5.4 道具快照

道具记录应包含精确类型与所有者，不能只记录裸地址：

```cpp
struct PropSnapshot {
    bool valid = false;
    ObjectIdentity identity;
    uintptr_t owner = 0;
    int32_t propTypeId = 0;
    std::string className;
};
```

在没有确认具体目标道具类和伤害调用链前，道具模块只实现发现、显示、日志和快照，不执行伤害相关写入。

## 6. 分阶段实施计划

### P0：停止错误写入

- 默认关闭当前道具伤害、道具范围和道具快攻写入。
- 移除 `FindAllProps()` 的模糊类名写入入口。
- 把所有普通 bool 写入改为 1 字节。
- 暂停使用 `self + 0xAB8` 作为 ChestPVE 库存入口。
- 未通过类型验证时返回失败，不使用默认值继续写入。

验收条件：开启诊断功能不会改变任何目标进程字段；错误模式和错误对象不会进入写入路径。

### P1：实现只读对象探针

调试面板至少显示：

```text
Self 地址 / 类名
识别到的模式
Inventory 候选偏移 / 地址 / 类名
Weapon 地址 / 类名 / 是否继承 AWeaponBase / 是否继承 AWeapon
CurrentProp 地址 / 类名 / PropTypeId / Owner
关键字段原始值及读取是否成功
最近一次拒绝写入的原因
```

建议同时输出带时间戳的文本日志，便于对照切枪、拾取道具、丢弃道具、死亡和重生事件。

验收条件：在 ChestPVE 场景中能够稳定观察到 `self+0xA98` 指向 `UMoeCharInventoryComponent`，并确认 `inventory+0xC8` 的实际对象类型。

### P2：修复快照和恢复框架

- 快照按对象保存，不再使用一组全局原始值。
- 使用显式 `captured` 状态。
- 恢复函数接收目标快照。
- 切枪时恢复旧地址，不查询新武器代替旧武器。
- 恢复前比较完整对象身份。
- 写入失败时保留快照并记录错误，不假装恢复成功。

验收条件：连续切换两把不同武器时，每把武器只恢复自己的原值；合法零值能够被保存和恢复。

### P3：按具体类型验证客户端表现字段

只对已经确认的 `AWeapon` 实例进行字段读取验证。每个候选字段分别记录：

| 验证项 | 需要观察的结果 |
|---|---|
| 值可读性 | 多帧稳定，数值范围与当前武器合理匹配 |
| 对象生命周期 | 切枪后旧对象不会被误写 |
| 本地表现 | 动画、准星、碰撞显示等是否变化 |
| 实际结果 | 是否仅本地表现变化，还是测试环境中的权威状态也变化 |
| 回滚 | 关闭功能、切枪、死亡后均能恢复 |

一次只验证一个字段，禁止把伤害、范围、攻速和持续判定同时开启，否则无法判断真正生效来源。

### P4：恢复具体道具类型

只有运行时日志确认目标道具后，才继续：

1. 确定目标的精确运行时类名和继承链。
2. 确定当前持有道具的直接引用链。
3. 通过 `PropTypeId` 和 Owner 进行第二重校验。
4. 区分配置字段、本地表现字段、复制字段和服务器结果。
5. 在授权测试环境中单字段验证。

若无法取得当前持有道具的直接引用，可以保留世界 Actor 扫描作为只读发现手段，但扫描结果不得直接进入写入路径。

## 7. 文档修正要求

原 `探灵实录武器内存功能分析.md` 中以下结论应标为“未验证”或删除：

- “电锯走 `AWeapon + WeaponFireComponent_Melee`”与“电锯属于 `AMoePropActorBase`”互相冲突。
- `self+0xAB8` 是 ChestPVE 库存组件的结论错误。
- “无 Net 标记等于客户端权威”的推导不成立。
- “DataAsset 非复制等于安全修改目标”的推导不成立。
- “ChestPVE 没有 Server Attack，因此客户端计算伤害”的证据不足。
- “`BP_ChestPVE_SupplyProp_ChainSaw_C` 已确认存在”缺少当前静态对象表证据。
- `NR3E` 的 Server Attack 与反作弊证据不能用于 ChestPVE 偏移，也不能被 ChestPVE 的结论覆盖。

建议将字段状态统一标记为以下四级：

| 状态 | 定义 |
|---|---|
| 已静态确认 | SDK 明确给出类、字段、偏移和宽度 |
| 已运行时确认 | 实际对象类名、继承链和字段数值均吻合 |
| 已本地表现确认 | 写入仅改变本地动画或显示 |
| 已授权环境结果确认 | 在可控测试环境中确认权威结果变化 |

不得从前一级直接跳到最后一级。

## 9. 推荐落地顺序

第一轮只改基础设施：

1. 增加字节读写接口。
2. 增加运行时类和对象身份校验。
3. 修正 ChestPVE 库存候选偏移。

1. 引入 `WeaponSnapshot`。
2. 修改所有恢复函数为显式目标。
3. 覆盖切枪、死亡、重生和退出场景。

3. 依据运行时证据更新原分析文档。

在完成前两轮前，不建议继续实现伤害倍率、持续伤害、范围伤害或飞剑伤害修改。
