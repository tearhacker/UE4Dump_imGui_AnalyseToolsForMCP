## MCP 网络配置三模式分析（产出 docs/MCP网络配置三模式分析与改造方案.md）

分析了 `mcp_server/客户端AI工具配置MCP文件.json` + `bridge.py` + 设备端 `src/mcp/`。

**核心结论：**
- 手机端 Operit **不需要 ADB**。Operit 与 UMT 同机同 network namespace，`127.0.0.1:35515` 直连可达。
  adb forward 只是「PC→手机」跨机隧道，同机场景是给自己转自己。
- 三种模式不在同一层：模式 1/2（192.168.x.x / 0.0.0.0）是**设备端 bind 地址**问题（改 C++）；
  模式 3（Operit 同机）是**协议/传输**问题（CommandServer 说私有 NDJSON，不是 MCP）。
- 模式 3 的 bind 地址不用动，`127.0.0.1` 已是正确答案。

**定位到的关键 bug：**
1. `bridge.py:44` `host: str = config.HOST` —— Python 默认参数导入期求值，运行时改
   `config.HOST` 完全无效，**加 `--host` 也不生效**（潜伏 bug）。必须改成 `host: str | None = None`。
2. `bridge.py:51-55` `_auto_forward` 恒为 True（`get_bridge()` 永远不传参），CLI 无开关关闭
   → 在手机上跑必挂。这是模式 3 的唯一硬阻塞。
3. `config.py:15-16` 的 `ADB_FORWARD_SPEC`/`ADB_FORWARD_ARGS` 是死代码，全仓库无引用；
   `adb.py:18` 又重复定义 `DEFAULT_PORT = 35515`。
4. `Protocol.hpp:16` `kBindAddress` 是编译期常量 → 模式 1/2 完全无法实现。
5. `CommandServer.cpp:229` `listen(fd,1)` + 单线程 accept→serve→close → Operit 与 PC 并存会 hang。

**方案（未实施，待用户确认）：**
- 改动 A（~12 行 Python，零 C++）：加 `--no-adb` / `--host`，让 Operit 的 Ubuntu 24 chroot 里
  直接跑现有 `server.py`，复用全部 tools.py 编排逻辑。
- 改动 B（~25 行 C++）：设备端 bind 从 `/sdcard/UnrealMemoryTools/mcp_bind.conf` 读取，
  默认仍是 `127.0.0.1`，非回环必须显式配置才生效（不放松安全红线）。

**Operit 侧事实核**：内置 Ubuntu 24（proot，共享宿主 netns，故 chroot 内可达 127.0.0.1）、
支持 MCP/Skill 市场、uvx/npx、远程 MCP。

## MCP IMGUI 日志可见性修复（设备端 C++）
用户痛点：AI 调工具时，IMGUI 运行日志只刷"客户端已连接/已断开"，看不到具体调了哪个工具/函数。
根因：设备端 `CommandServer::HandleFrame`（收到 {id,cmd,args}）和 `CommandDispatcher::PollOnce`（执行命令）都**不打印命令名**，连接上下线却是 LOGI，于是淹没一切。
修复（已增量编译 + llvm-strings 确认新串在产物内）：
- `CommandServer.cpp`：收到命令即 `LOGI("[MCP·调用] %s id=%llu args=%s")`（args 超 240 字截断）。
- `CommandDispatcher.cpp`：执行前 `LOGI("[MCP·执行] %s")`；正常完成 `LOGI("[MCP·完成] %s 耗时 %lldms")`（超时仍走原 LOGE）。
- 连接上下线改前缀 `[MCP·连接]`，与调用日志区分。
- `executable.cpp` 运行日志面板加"隐藏 MCP 连接上下线"勾选框，勾选后过滤 `[MCP·连接]` 行。
结论：现在日志能清楚看到"AI 调了什么工具 + 在做什么 + 耗时"，连接刷屏可一键屏蔽。

## 连接刷屏根因 + 重连合并（CommandServer.cpp）
继续排查"持续显示客户端已连接/已断开"：确认 PC 侧 `tools.py` 走 `br.call()` 单例 bridge，**不会**每个工具新建连接。
所以刷屏是 bridge 连接本身在反复断重连（MCP 宿主对 server.py 每轮调用重生子进程，或 adb forward 不稳），属设备外问题。
设备侧能做的：把"断开后立即又连上"的重连风暴合并成单行，避免成对刷屏。已在 `ServerLoop` 加：
- `static time_t s_lastConnectTs/s_lastDisconnectTs` + `kConnCoalesceSec=5`；
- 距上次断开 <5s 的连入只打 `I: [MCP·连接] 重连（距上次断开 Xs）`，不重复"已连接"；
- 若本次连接持续 ≥5s 才单独打"客户端断开"，否则被下次"重连"行概括。
效果：正常长会话仍显示 已连接/已断开；重连风暴每轮只剩一行"重连"，配合面板"隐藏 MCP 连接上下线"开关双保险。
增量编译通过，llvm-strings 确认新串在产物内。
