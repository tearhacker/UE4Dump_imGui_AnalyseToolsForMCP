## 真实目的：给 Andriod_UnrealMemoryTools 做自己的 MCP（可行性分析）

用户真实意图：为自己的 UE4 Dumper 项目也开发一套 MCP 工具。结论：**可行，且比 Zygisk 方案简单**（自身即独立进程，不需注入/hook）。

### 项目性质（关键）
- 外部 Dumper，**不注入不 hook**，纯 `/proc/<pid>/mem` 读内存；独立 ELF 二进制，Vulkan + ImGui 悬浮窗。
- 需要 root。构建：NDK r25+ / CMake + Ninja / clang C++20，产物 `outputs/arm64-v8a/`。
- 输出目录 `/sdcard/UnrealMemoryTools/<package>/`（Logs.txt、Objects.txt、Offsets.hpp、SDK_*.hpp、script.json、libUE4.so）。

### 已具备的 MCP 基础设施（executable.cpp）
- `DumpUiState` + `std::mutex`（110-135 行）：UI 每帧加锁 poll 的共享状态，命令服务可直接复用此模式。
- `gWorkerThread` + `ExecuteProbe` / `ExecuteDump` / `ExecuteDumpUnrealLib`（945-989 行）：单 worker 跑重活。
- `PushUiLog` / `LoggerSink`（227-242 行）：日志已结构化收在内存。
- API 边界干净：`UEDumper::Init(profile)` / `UEDumper::Dump(buffers)`（Dumper.hpp:31-33）。
- `FindAutoProcessCandidates()`（166 行）枚举进程；`SDKExplorer.cpp`（137-511）有对象检索 + 属性面板。
- `main()` 在 1761 行，`while(flag)` 渲染循环在 1805 行，`Layout_tick_UI(&flag)` 每帧调用。

### 方案设计
- **方案 A（推荐）**：进程内加命令服务线程 → 命令队列（mutex + cv）→ 复用 gWorkerThread 执行 → 状态/结果回写轮询。
  长任务必须异步化（投递回 job_id，另用 job_status 轮询），否则阻塞 MCP 通道（源项目就吃了这个亏）。
  建议端口 27185，避开源项目 27184。
- **方案 B（保底）**：加 `--headless --cmd "..."` 参数，跑完 print 到 stdout 退出，MCP 层用 `adb shell su -c` 调。
  零线程改造最安全，但每次冷启动且无法保持已探测状态。
- 风险：Vulkan/ImGui 悬浮窗依赖屏幕（灭屏 ANativeWindow 可能失效 → 建议 headless 跳过图形初始化）；
  root 权限；adb forward 仅 localhost 生效。

- AI 的价值是「提候选」，偏移来自 dump 的真实数据，两者不可互换；真正的杀手锏是

## AutoFix 失败根因定位（代码级，重要）

用户痛点：某些**单机游戏** AutoFix 搜不出 GNames / UWorld，探测直接失败。已定位到具体硬编码点。

### 致命依赖链
`IGameProfile::GetGUObjectArrayPtr()`（UEGameProfile.cpp:893）第一行
`const uintptr_t namesPtr = GetNamesPtr();`（:900），拿不到就 `return 0`。
→ **GNames 一挂，GUObjectArray 连尝试都不做，GWorld 一并全崩。**

### GetNamesPtr() 的四个硬编码卡点（UEGameProfile.cpp:971 起）
| 卡点 | 位置 | 后果 |
|---|---|---|
| 指针值范围 `0x4FFFFFFFFF~0x7FFFFFFFFF` | :995-996 | 分配器布局不同则一个候选都进不来 |
| FNamePool 锚点偏移 `val + 0x8` | :1030 | 条目头长度变了就永远读不到 |
| GNames 锚点偏移 `p1 + 0x24` | :1046 | 同上 |
| 锚点字符串**只有 "ByteProperty"** | :999-1001 | 该 FName 不在预期位置即判定失败 |

### 白捡的改进点
`UEGameProfile.cpp:80-84` 已有完整多锚点名单
（None/ByteProperty/IntProperty/BoolProperty/FloatProperty/ObjectProperty/NameProperty/
StructProperty/ArrayProperty/Object/Class/Function），
但**只在 `BruteForceDeltaForceNames`（三角洲专用）里用**，通用路径没用上。
→ 把多锚点验证接到通用路径，是**不需要 MCP 的纯 C++ 小改动**，可能立刻救活一批游戏。

### 其他事实
- `DetectVersion()`（AutoFix.cpp:140）：先 `GuessMajorFromSoName()`（libUnreal.so→UE5_03），
  否则扫 rodata 的 `++UE4+Release-X.YY`；**找不到字符串就默认 UE4_25_27**（可能选错偏移表）。
- 扫描范围只在 `ue_elf.segments()` 内找"存在 ELF 里、指向 name pool 的指针"，
  堆上/其他模块的指针扫不到。

### MCP 方案要点
- **分工铁律：扫描必须在设备端 C++ 跑，AI 只负责"换假设 + 判结果"**。
  几百 MB 内存走 adb 给模型看既慢又无意义。
- 需要新增的工具：`ue_detect_version`、`names_scan`（参数化 min/max ptr + 锚点数组 +
  锚点偏移 + 扫描区域）、`names_sample`（返回候选的前 N 个 FName 字符串 ← AI 判断的命脉）、
  `objects_scan`（接受 names 候选 id，解开依赖）、`memory_read*`、`probe_apply`。
- AI 比静态启发式强的地方：启发式只能判"12 字节是否等于 ByteProperty"；
  AI 能判"这 16 个字符串序列像不像 UE 的 FName 表"，信息量与容错都高一个量级。

### 诚实边界（已告知用户）
FName 加密/混淆的游戏（明文锚点失效）AI 也难办；全内存扫描慢，需容忍几十秒；
能显著提高命中率但不能保证 100%（当前硬编码不匹配时是 0%，目标 70-80%）。

## 用户背景补充与自主性设计定案

### 背景
- 源码原作者曦曦(DreamFekk)已停更，用户是在此基础上自己往下做。
- 主要场景：**单机游戏**，包括**用户自己开发的 UE4 手游**。→ 性质属于正当逆向/自研调试。
- 用户诉求：希望 AI 能"产生自己的智慧"——自主搜索、独立判断、跳指针、分析内存，甚至断点调试。

### 定案的设计原则（后续开发必须遵守）
1. **原语 vs 领域工具 = AI 自主性的上限**。
   只给 `find_gnames()` 这类任务工具 → AI 只能做写死的事；
   给足 `read_ptr/read_bytes/scan/list_modules/resolve_symbol/read_maps` → AI 能拼出未预置的策略。
   **四层结构**：AI（顶层循环）→ 领域工具（names_scan/class_search/probe，快路径）
   → 复合操作（follow_chain/scan_candidates，省轮次）→ 原语（AI 的手）。
2. **跳指针是 AI 的强项**：每步解引用后判断"这个值合理吗"（落在哪个模块、像不像数量、
   字符串像不像 UE 名字），这类语义判断正是固定脚本最弱的地方。
3. **三条工程约束**：
   - 轮次预算：纯原语会爆炸（10 层指针 × 5 候选 = 50 次调用），必须用"复合操作"层折中
     （一次调用走 N 层，返回整条链）。
   - 验证纪律：工具必须返回**原始观测值**（十六进制/字符串），绝不返回"看起来对"的总结。
   - 护栏：自主模式**默认只读**；写内存/打断点需显式开关，并用 MemoryBackup 支持撤销。

### 断点调试：需要独立子系统，不能靠 MCP 凭空给
- UMT 是外部进程，断点必须走 ptrace attach（root 下可行）或注入。
- 难点：SIGSTOP 停进程破坏时序、反调试检测；ARM64 硬件断点要走
  PTRACE_GETREGSET / NT_ARM_HW_BREAK，且是**per-thread**，需枚举目标所有线程。
- 结论：**独立立项，工作量可能超过 MCP 桥本身**。建议先做只读分析 + 内存扫描。

### 测试策略（用户优势）
用户自己的 UE4 手游 = **有 ground truth**（真实 GNames/GWorld 地址已知），
可量化 AI 命中率、定位失败发生在哪一步；同时用户掌握确切 UE 版本，
可用来校准 `DetectVersion()` 是否判断错误。这是最理想的测试床，优先用它验证。
（但用户强调：真正要解决的是**第三方单机游戏**，他什么都不知道的情况。）

## 关键定案：自主定位不需要外部特征码（核心设计）

用户质疑："第三方游戏我不知道 GNames/GWorld，怎么给 AI 特征码？"
→ **答案：不需要给。特征码（ADRP+LDR 模式、ByteProperty 字节串）是老办法的思路，
   属于 per-game 适配。自主定位走的是「结构不变式 + 引擎级名字表」，对所有 UE 游戏通用。**

### 三个通用锚（不依赖任何游戏知识）
1. **版本字符串**：`++UE4+Release-X.YY` / `++UE5+Release-X.Y` 在几乎所有 UE 二进制的 rodata 里
   （现有 `ScanVersionString()` 已实现）→ 拿到版本 → 选中偏移表。
2. **引擎级名字表**：FName 表前若干个条目**在所有 UE 游戏里都一样**——
   None / ByteProperty / IntProperty / BoolProperty / FloatProperty / ObjectProperty /
   NameProperty / StructProperty / ArrayProperty / Class / Object / Function / Package。
   这不是"特征码"，是**引擎固有内容**，跨游戏恒定。
3. **结构自洽性**：猜对 GUObjectArray 时，上万个对象会互相交叉验证
   （obj->Class / obj->Outer 都落回同一数组，obj->Name 索引能经 GNames 解出合理字符串）；
   猜错则立刻崩散。**这是自洽检验，零外部知识。**
4. **GWorld 根本不需要单独扫**：一旦 GUObjectArray 可用，
   GWorld = 在对象数组里找 class 为 `World` 的实例（现有 `FindObject` 类接口即可）。

### 漏斗式扫描（速度关键）
全部可读内存(~800MB) → 指针对齐+落点可读筛选(~50万，设备端廉价判断)
→ 结构验证能解析出 FNameEntry(~200，设备端) → **AI 看每个候选的前 16 个字符串样本(PC 端)**。
**昂贵的 AI 步骤永远只接触约 200 份小样本，不碰原始大内存。**
提速手段：先扫最可能区域（UE 模块 .data/.bss）再扫全堆；
置信度达到阈值（如 5 个引擎名全中）早停；候选集按 session 缓存，AI 换判据时不必重扫。

### AI 不可替代的环节（对用户"AI 自己分析"诉求的准确回答）
AI 不是去扫内存，AI 是**能容忍噪声的验证器**。
硬编码打分器要求"12 字节精确等于 ByteProperty"（是非题，容错为零）；
AI 判断的是"这 16 个字符串序列像不像 UE 的 FName 表"（语义整体判断，
即使其中 2 条读错仍可判定）。这是自动化成功率的关键差异。

### 仍然无解的情况（已如实告知）
- FNameEntry 被加密或游戏自定义了名字池 → 结构不变式失效，只能回到代码特征定位
  `FName::GetNames()`，需要反汇编能力，难度大得多（单机游戏里相对少见）。
  **补充：29 个 AndUEDumper profile 里只有 DeltaForce 覆写了 `GetNameEntryString`
  解密钩子 → 加密 FName 实际占比约 3%，不是普遍问题。**
- 二进制被 strip 导致版本字符串丢失 → 退化为"逐个尝试所有版本偏移表"，慢但仍可行。
- libUE4.so 被改名/静态链接 → ELF 探测失败，需改为扫描所有可执行模块找 UE 特征。

## 新素材：AndUEDumper（UMT 的上游）— 重大发现

路径：`D:\泪心安卓领域基本盘技术\ue4ImGuiAutoWorkingMcpBytear\AndUEDumper\AndUEDumper\src\UE`

### 核心发现：pattern 不是"游戏特征码"，是"引擎函数序言"
`UEGameProfiles/Torchlight.hpp` 的注释明写：
`FNameEntry const* FName::GetEntry(FNameEntryId id);`、`DebugDump`、
`GetPlainName ToString AppendString GetStringLength` —— 全是 **UE 引擎函数**。
→ 字节序列由「UE 版本 + 编译器」决定，**跨游戏可迁移，与具体游戏无关**。
佐证：29 个 profile 里 17 个都用 `UE4_25_27` 偏移表。

### 按版本聚合的可用 pattern 数（白捡的资产）
| UE 版本 | pattern 数 | 来源游戏数 |
|---|---|---|
| UE4_25_27 | **211** | 17 |
| UE4_23_24 | 39 | 3 |
| UE5_00_02 | 42 | 3 |
| UE5_03 | 28 | 2 |
（UE4_25_27 是手游最常见的一档）

### UMT 丢了数据但能力还在
- UMT 只保留 6 个 profile（暗区突围/三角洲/远光84/天堂2/夜鸦(NRC)/PUBG）
  + 自研 PUBGMHD/Sfps2/Valorant，**丢了 AndUEDumper 的 23 个**。
- 但机制全在：`findIdaPattern()`（`UEGameProfile.cpp:834`）、
  `Arm64::DecodeADRL()`（`UEMemory.hpp`，且比上游多了 Decode_ADRP_ADD / Decode_ADRP_LDR）、
  `PATTERN_MAP_TYPE`（ANY_R/ANY_X/ANY_W/BSS）、`isEmulator()`。

### 定案：双路径定位（修订原计划）
1. **快路径**：版本检测 → 挑该版本的 pattern 库 → findIdaPattern → DecodeADRL → 候选（秒级）
2. **兜底**：全内存结构扫描（分钟级，不依赖 pattern）
3. **两条路共用同一个验证环节**：解析前 16 个名字看是否引擎名表 → AI 判定
   → 互为交叉校验，误判率大幅下降。

### 修订后的行动顺序（原"先做多锚点"改为先抽 pattern 库）
1. 从 AndUEDumper 抽取 pattern，按版本去重整理成表（纯数据，零风险，收益最大）
2. 多锚点接进通用路径（纯 C++ 小改动）
3. MCP 工具规格草案
4. 断点调试另立项

### 注意
pattern 会随游戏更新失效（这正是 AutoFix 诞生的原因），**不能只靠 pattern**，
必须保留结构扫描兜底。

## 用户追问：上 hook 能否解决那三种无解情况 — 结论

用户设想：给 MCP 加上 Dobby / perf 断点等注入能力，是否就能解决三个难题。
**答案：1 个决定性、1 个间接、1 个无关。**

| 情况 | hook 是否有效 | 机制 |
|---|---|---|
| ① FName 加密/自定义名字池 | **决定性** ✅ | hook `FName::GetEntry(id)` / `FName::ToString()`，让游戏自己解密，
  无需知道加密算法（对比：AndUEDumper 的 `GetNameEntryString` 虚函数要求你"知道怎么解密"）。
  **ptrace 远程调用即可，不需完整注入。** |
| ② 版本字符串被 strip | 间接 ⚠️ | hook 变不出已删除的字符串；但可在进程内调用引擎运行时版本 API，
  或靠访问器绕开"必须先知道版本"的前提。且"挨个试偏移表"本来也能跑。 |
| ③ libUE4.so 改名/静态链接 | **无关** ❌ | 这是探测问题不是访问问题。解法是枚举 /proc/pid/maps 所有可执行模块
  逐个检查 UE 特征（而非按文件名找），纯外部就能做。 |

### hook 的真正价值（比救三个边角重要得多）
**"猜偏移"这件事本身可以被绕过**：有进程内调用能力后，
名字调 `FName::ToString()`、类型判断调 `UObject::IsA()`、属性偏移问 `FProperty::GetOffset()`。
→ **偏移从"前提"降级为"兜底"，是范式变化。**

### 三级能力阶梯（定案）
1. 外部只读（成本低，现在就能做）
2. **ptrace 远程函数调用**（成本中，痕迹小，能解 case ① ← 最容易被忽略但性价比最高）
   attach → 保存寄存器 → 设参数+PC → 继续 → 读返回值 → 恢复 → detach
3. 完整注入 Dobby（成本高，稳定性风险，覆盖全部）
   代价：项目性质改变、稳定性（用户自己另一个项目就在修 4h 长跑稳定性）、
   maps 痕迹、工作量比 MCP 桥本身还大。

### 战略建议（已告知用户）
**不要凭空建注入层**。实测 case ① 占比约 3%，case ③ 手游罕见，case ② 本来就能跑；
真正常见病是硬编码指针范围/单锚点/GNames 依赖链。
→ 先做外部方案 + AI 验证闭环，**拿 10 款游戏实测统计"失败在哪一步"**，用数据决策是否上注入。

## 重大发现：ptrace 远程调用能力已在 KittyMemoryEx 里，且完全可用

**`KittyTraceMgr::callFunctionFrom()`（KittyTrace.cpp:140）是完整正确的远程函数调用实现，
一直在依赖里没人用。** 已逐条核实：

| 能力 | 状态 | 位置 |
|---|---|---|
| ATTACH/DETACH/CONT/WAIT | ✅ | KittyTrace.cpp:28/38/50/71 |
| 寄存器备份恢复（自动选 GETREGSET） | ✅ | getRegs/setRegs |
| ARM64 参数填充 x0–x7 | ✅ | tmp_regs.uregs[i] 循环 |
| >8 参数压远端栈 | ✅ | sp -= ... + Write |
| 返回检测 LR 陷阱 | ✅ | tmp_regs.lr = callerAddress |
| 捕获 SIGSEGV/SIGILL 判返回 | ✅ | WSTOPSIG 判断后 break |
| 区分 WIFEXITED / WIFSIGNALED | ✅ | 有处理 |
| 失败自动恢复寄存器 | ✅ | _autoRestoreRegs |

API：`callFunction(addr, nargs, args...)` / `callFunctionFrom(caller, addr, nargs, ...)`
（`KittyTrace.hpp:114-122`），另有 `setDefaultCaller()` / `setAutoRestoreRegs()`。

### 剩下只需 100-200 行胶水
1. 找函数地址 ← **pattern 库正好干这个（两者是紧耦合上下游）**
2. `FName::ToString(FString&)` 需要可写 scratch 缓冲区（从 maps 挑一块可写区）
3. 读回 FString 结构（data 指针 + 长度）再读字符串本体
4. 接进 probe 流程

### 仍然成立的物理限制
**ptrace 只能"开锁"不能"搬货"**：每次调用要 attach→设寄存器→继续→等信号→取返回值，
进程全程冻结。
- 验证环节（几十次调用）= 毫秒~秒级 → **完美胜任，且与 AI 验证闭环天作之合**
  （AI 判断一个候选只需 16 个名字样本 = 16 次调用）
- 全量 dump（几十万次）= 进程冻结数分钟 → ANR/看门狗，不可行

### 已知缺陷需兜底
SIGSEGV/SIGILL 返回陷阱**无法区分"陷阱触发"与"被调用函数自己崩了"**（信号相同）。
兜底：校验返回值 —— 检查指针可读、字符串是否像 UE 名字（崩了会返回垃圾，一验就露馅，
且这恰好是 AI 擅长的）。

### 冻结风险分析（用户追问"会不会导致闪退"，已答）
| 风险 | 阈值 | 是否杀进程 |
|---|---|---|
| ANR（主线程不响应输入） | 5s | **不自动杀**，只弹系统对话框，可选等待 |
| 游戏自带看门狗（UE 有 hang detector） | 各家不同 | **会 abort**，是真正的闪退来源 |
| 服务器踢线 | 各家不同 | 会断连 —— **单机游戏不存在此风险** |
| 系统杀后台 | 仅后台/息屏 | 与 attach 无关 |

**量化**：attach 开销是"每次 attach 一次"，不是"每次调用一次"。
正确做法 = attach 一次 → 内部连续调 N 次 → detach。
单次调用约 1-5ms，开锁阶段 16 次 ≈ **30-80ms**，距 ANR 的 5s 差两个数量级 → **安全**。
搬货阶段几十万次 → 分钟级 → 必触发看门狗 → 不可行（故搬货必须走 /proc/pid/mem，全程不 attach）。

**比闪退更隐蔽的风险是死锁**：若只挂单个线程让游戏继续跑（ptrace 可指定 tid），
调用 `FName::ToString` 可能撞上游戏持有的锁（FNamePool 有临界区）→ 死锁。
权衡：挂全进程（group-stop，无死锁，但必须短）vs 挂单线程（不冻结，但可能死锁）。
→ KittyTrace 现有实现是 `ptrace(PTRACE_ATTACH, remotePID())` = 挂全进程，**正合用**。

**缓解清单**：单次 attach 内批量调用 / attach 前先快照关键内存 / ptrace 失败回退结构扫描 /
前台操作保持极短。

**最重要的建议（已告知用户）：不要理论，去测。**
用户有自己的 UE4 游戏 → attach 后保持 100ms / 1s / 5s 递增，观察是否闪退，
10 分钟即可测得真实安全窗口。这是最可靠的答案来源。

## 加密 FName 解密所需的 MCP 工具设计（四层）

### 前置事实（已核实）
- **设备上没有反汇编器**：只有 `KittyMemoryEx/Deps/Keystone/` 头文件，
  且 CMake 用 `-DkNO_KEYSTONE` 关掉了。KittyArm64.hpp 无可用公开接口。
- `KittyScanner` 齐全：findBytesAll/First、findHexAll/First、
  **findIdaPatternAll/First**、findDataAll/First。
- → **反汇编放 PC 侧做**（MCP server 里 pip 装 capstone），设备零负担、零体积代价。
  **这是让 AI 能"像人一样读汇编"的关键，也是本设计的点睛之笔。**

### 四层工具
1. **定位层**：`scan_pattern`（IDA 风 pattern）· `resolve_symbol` · `elf_symbols` · `read_memory`
2. **理解层（PC 侧）**：**`disassemble(hex_bytes, base_addr)` ← capstone** · `decode_adrl`（UMT 已有）
3. **准备层**：`scratch_alloc(size)`（ptrace 调目标进程的 mmap 拿可写区）· `memory_write`
4. **调用层**：`attach_begin/end`（会话式，一次冻结内多次调用）
   · `call_function(addr, args[], return_kind)` · `call_function_batch`
   · `read_string(addr, max_len, wide)`（FName 可能是 UTF-16）

### AI 解密 FName 的实际流程
scan_pattern 找 GetEntry/ToString → disassemble 看汇编判断签名（几参、是否 sret）
→ scratch_alloc 备 FString 输出缓冲 → attach_begin
→ call_function × N → attach_end → read_string × N → AI 判"像不像 UE 名字表" → 收敛或换 pattern 重来

### 批量问题的解法（把"必须注入"降级为"慢但可行"）
**分块批处理 + 块间放行**：测出安全窗口（如 1s）→ 每块调用数 = 窗口/单次耗时
→ 每块结束 detach 让游戏跑一会儿 → 循环。
- **AI 分析场景：只需几百个名字 → 几块 → 几秒搞定，加密几乎无影响。**
- 全量 dump（50 万名字）→ 数十分钟到一小时，慢但游戏不死；
  且这是 3% 的罕见兜底路径，可以接受慢（甚至跑一晚上）。

## 技术栈定案（架构文档 §5.0，v1.1 新增）

### ❗前提纠正（重要，用户误以为源项目是 FastMCP）
**源项目 `mcp_server.py` 不是 FastMCP，是纯标准库手写**
（import 仅 argparse/json/math/os/socket/struct/subprocess/sys/threading/dataclasses/typing，
无任何 MCP SDK，JSON-RPC 2.0 手工实现）。
→ 它那些限制（无 resources/logging/progress/cancellation、单线程串行阻塞）
**是手写实现的代价，不是 MCP 本身的限制。不要当范本照抄。**

### 选型结论
```
设备端：C++20（已定，无选择余地）
PC 侧 ：Python 3.11+ / 官方 MCP SDK 的 FastMCP（mcp.server.fastmcp）/ capstone
```

**决定项 1：capstone。** `disassemble` 是核心工具（加密 FName 解密靠它读汇编），
Python 有成熟原生绑定；Node 生态弱（capstonejs 长期失修，需 WASM 或原生插件）。
→ **这一条直接排除 TypeScript。**

**决定项 2：SDK 白送 resources / logging / progress / cancellation**，
正是 v1.1 审查要补的四项。手写等于重做 SDK 的活，还容易做错。

- 用**官方 `mcp` 包里的 FastMCP**，不用第三方 `fastmcp` 包（社区版与官方协议节奏不同步）
- **必须锁版本**：MCP 协议一年迭代 4 个版本，SDK churn 快
- FastMCP 同一套工具定义可跑 stdio / HTTP → 直接满足最佳实践 3.1（IoC）

### ⚠️ 两个必须注意的坑
1. **FastMCP 是 asyncio 的，设备 I/O 是阻塞的**（探测可能几分钟）。
   绝不能在 async 函数里直接同步 socket 调用 → 会卡死事件循环，
   progress/cancel/其他工具全部停摆。必须用 `await asyncio.to_thread(...)`。
2. **Pydantic 生成的 schema 必须与文档一致**。41 个工具手写 inputSchema/outputSchema
   极易与实现漂移 → 用类型注解 + Pydantic 自动生成，再写单测反过来校验文档里的 JSON Schema。

### 依赖策略修正

### 事实纠正：不是"删除"，是从未移植
查 UMT git 历史，那 24 个文件**从未存在过**（`git log --diff-filter=A` 为空）。
UMT 作者是重写时另选了一批游戏。**不是删 CN 项目。**

### 直接搬运会编译失败（重要）
UMT 基类有 4 个 AndUEDumper profile 没有的**纯虚方法**：
`GetMatrix()` / `GetPhysx()` / `GetFrameCount()`（`= 0`），
AndUEDumper 基类根本没有这三个（UMT 作者后加的）。
→ 移植每个 profile 都要补这三个桩（返回 0 即可，AutoFix 就是这么做的）。

**更关键的架构分歧**：
| | AndUEDumper | UMT |
|---|---|---|
| GetGUObjectArrayPtr / GetNamesPtr | `= 0` 纯虚，每个 profile 写死 pattern | **有默认实现** = 通用自主定位 |

→ 搬一个 AndUEDumper profile 进来 = 用游戏专用 pattern **覆盖掉 UMT 的通用定位**，
与"自主定位"战略相反。**所以正确做法不是搬 profile，是抽 pattern。**

### 精确抽取结果（**修正早期 grep 粗估**）

### 🔴 重大发现：符号定位才是最快的第一路径（v1.0 漏了）
**28 个 profile 里 19 个的第一策略是符号定位，不是 pattern。**
ArkUltimate 的写法是：先 `findSymbol("GNameBlocksDebug")`，失败才走 idaPatterns。

四个引擎原生符号（跨版本稳定）：
| 符号 | 用途 | 覆盖 |
|---|---|---|
| `GUObjectArray` | 对象数组 | **全版本** |
| `GNameBlocksDebug` | 名字表（解引用后回减 FNamePool.BlocksOff） | UE4.23 → UE5.03 |
| `_ZN5FName16GetIsInitializedEv` | 名字表（需 DecodeADRL） | UE4.00–4.20 |
| `GFNameTableForDebuggerVisualizers_MT` | 名字表（直接即地址） | UE4.22 |

**修正后的定位优先级（已写入两份文档）**：
```
① 符号定位    O(1) 最快最稳  ← v1.0 漏掉的就是这条
② pattern     秒级，按版本挑
③ 结构扫描    分钟级，兜底
④ ptrace 调用 加密时让游戏自己解
```
理由：符号表查找 O(1) vs pattern 扫段 O(n)；符号名是源码标识符，比字节序列稳定。
