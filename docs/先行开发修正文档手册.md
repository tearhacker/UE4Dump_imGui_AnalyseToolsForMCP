## 3. 代码差异定位清单（MCP 版 vs 原始版）

### 3.1 完全一致的文件（无需改动 ✅）

| 文件 | 差异 |
|------|------|
| `src/AutoFix/AutoFixOffsets.cpp`（3185 行） | **0 差异** |
| `src/Dumper.cpp` | **0 差异** |

### 3.2 `src/UE/UEOffsets.cpp`（真实逻辑差异 3 处）

#### 🔴 差异 1：`NumElements` 偏移 0x14 → 0x10（两处）

| 版本函数 | 原始版 | MCP 版 |
|----------|--------|--------|
| `UE4_20` | L471: `(sizeof(void*)*2) + sizeof(int32_t)` = **0x14** | L474: `sizeof(void*) + (sizeof(int32_t)*3)` = **0x10** |
| `UE4_23_24` | L570: `(sizeof(void*)*2) + sizeof(int32_t)` = **0x14** | L584: `sizeof(void*) + (sizeof(int32_t)*3)` = **0x10** |

- `UE4_25_27` 继承 `UE4_23_24` → LetsGo（回退 UE4_25_27）读 `NumElements` 用 **0x10**（MCP）vs **0x14**（原始）。
- `UEWrappers::GetNumElements()` / `GatherUObjects` 均依赖此偏移。
- ⚠️ 备注：历史修复记录称"UE4.2x 应为 0x10"（UE 源码布局），但原始版用 0x14 且探针成功，说明 Dumper7 偏移语义与 UE 源码布局不同，以 Dumper 实测为准。

#### 🔴 差异 2：`FNamePoolEntry.GetLength` header 解包规则

```cpp
// 原始版：二选一
return bWITH_CASE_PRESERVING_NAME ? header >> 1 : header >> 6;

// MCP 版：先 >>6 后回退 >>1（兼容 16 位 header / UE4.26+）
if (bWITH_CASE_PRESERVING_NAME) return header >> 1;
size_t len = header >> 6;          // 32 位 header (4.22-4.25)
if (len == 0) len = header >> 1;   // 16 位 header (4.26+)
return len;
```

- MCP 版为兼容腾讯魔改 UE4.26 的 16 位 header 而放宽。**理论上更正确**，不构成 LetsGo 失败根因。

#### ✅ 差异 3：`UE5_00_02` 的 NumElements 保持 0x14（两版一致）

### 3.3 `src/UE/UEGameProfile.cpp`（差异 393 行，4 组实质差异）

#### 🔴 差异 A：`GetGUObjectArrayPtr()` 主循环 ID 过滤（两版一致但未适配 outline）

#### 🟡 差异 C：MCP 版新增 override 机制

- `SetAddressOverrides()`（L14-31）、`_addressOverrides` 分支（L712-756）。仅 MCP 工具显式下发时生效。

### 3.4 `src/UE/UEGameProfiles/AutoFix.cpp`（全文件重写，最可疑 🔴）

#### 🔴 差异：LetsGo 强制 outline（MCP 新增，原始版没有！）

```cpp
// MCP 版 L186-187（原始版完全没有）
if (_packageHint == "com.tencent.letsgo" || _packageHint == "com.tencent.tmgp.yuanmeng")
    _outlineNumber = true;

// 原始版：LetsGo 走 UE4_25_27 家族时 _outlineNumber = false（L177）
```

- 影响：MCP 版 `GetNameEntryString()` 会走 outline 外链逻辑（`GetLength(header)==0` 时跟随 nextEntryId），原始版不会。

### 3.5 `src/UE/UEWrappers.cpp`（差异 110 行，2 处实质）

| 差异 | 原始版 | MCP 版 |
|------|--------|--------|

## 4. LetsGo 失败根因链分析

### 4.1 最新失败日志（pid 16655）

```
W: [AutoFix] UE version string not found; fallback to UE4.25-4.27
I: [Bootstrap] FNamePool @ 0x76d559dd90 (slot @ 0x76d559ddd0, anchorOff=0xc, hits=1)
I: [Bootstrap] verifyCandidate(mem-ok,name-fail): cand=0x76d559dcf0 objects=0x76d559dca8 chunk0=0x76d559dbb8 obj0=0x76c7fbb928 id=1392538734 name=''
I: [Bootstrap] verifyCandidate(mem-ok,name-fail): ... id=1635013490 name=''
I: [Bootstrap] verifyCandidate(mem-ok,name-fail): ... id=1836016485 name=''
E: [Bootstrap] 通用方式搜索 GUObject 失败
I: [Bootstrap] 诊断: NamesPtr=0x76d559dd90, scanBase=0x76d559dd90, nameOff=0x18, objObjectsOff=0x10
E: 探针失败: ERROR_INIT_GUOBJECTARRAY
```

### 4.2 直接原因链

1. **FNamePool 命中成功**：`namesPtr = 0x76d559dd90`，多锚点扫描正常工作。
2. **对象槽位 FName index 是 outline number**：`id=1392538734 = 0x53000002`（真实 index = `>>18 = 5287`，已知 LetsGo 开 `FNAME_OUTLINE_NUMBER`）。
3. **主循环过滤把 outline number 全跳过**：`if (id <= 0 || id > 0x200000) continue;` → `0x53000002 > 0x200000` → continue → 锚点 `/Script/CoreUObject` 永不匹配 → `verifyCandidate(mem-ok,name-fail)`。
4. **诊断分支也无解包**：`GetNameByID(0x53000002)` → `GetNameEntry` 用 outline number 本身算 `block_offset = (0x53000002>>16)*8` → 巨大偏移 → 读不到 → `name=''`。
5. 双向扫描（UP/DOWN 各 0x300000 范围）全部候选失败 → `ERROR_INIT_GUOBJECTARRAY`。

### 4.3 与原始版的路径差异（为什么原始版能成功）

- 原始版对 LetsGo **没有强制 `_outlineNumber=true`**（`AutoFix.cpp` 无 L186-187 两行）→ 不跟 outline 外链，路径简单。
- 原始版 `NumElements=0x14`、`GetNumElements()` 无范围校验 → 与 MCP 版行为不同。
- 结论：**MCP 版为了兼容 LetsGo 加的 outline 强制 + NumElements 改动，反而引入了与原始成功路径的偏差**。

## 5. pubgmhd 失败根因分析

### 5.1 现象

- `com.tencent.tmgp.pubgmhd`（UE4.18）：FNamePool 命中，`GetGUObjectArrayPtr` 双向扫描全候选 `verifyCandidate(mem-ok,name-fail)` → `ERROR_INIT_GUOBJECTARRAY`（专用 Profile + AutoFix 回退均失败）。

### 5.2 根因假设

- `PUBGMHD.hpp` 硬编码 `IsUsingFNamePool()=false`（按 UE4.18 老式 GNames 走），但设备端实际扫到 FNamePool → 名称解析全错位 → 锚点恒失败。
- 镜像 LetsGo 教训：LetsGo 是"实际 outline 但未开启"（已加强制），pubgmhd 是"实际 FNamePool 但硬说不是"。
- 次要：`objObjectsOff=0x10` / `nameOff=0x18` 均为默认预设，pubgmhd 魔改布局未验证。

## 6. 修正方向（按优先级）

> 以下为修正建议，**当前未执行**。

### P0-1：verifyCandidate 适配 outline number（`UEGameProfile.cpp:1094`）

```cpp
// 现状（两版一致）：
if (id <= 0 || id > 0x200000) continue;

// 修正方向：outline 模式下先解包再过滤
const int32_t rawId = id;
if (isUsingOutlineNumberName())
    id = rawId >> 18;   // FNAME_OUTLINE_SHIFT
if (id <= 0) continue;
```

### P0-2：`GetNameEntry()` 支持 outline 解包（`UEGameProfile.cpp:788`）

```cpp
// 在 FNamePool 分支入口处：
if (isUsingOutlineNumberName())
    id >>= 18;   // outline number → 真实 FName index
```

> ⚠️ 注意：历史上曾无条件加 `id>>18` 导致其它游戏坏掉，必须**条件化**（仅 `isUsingOutlineNumberName()` 为 true 时生效）。

### P0-3：复核 `NumElements` 偏移（`UEOffsets.cpp:474,584`）

- 用 LetsGo 真机实测确认 `ObjObjectsPtr + 0x10` 还是 `+0x14` 才是元素个数。
- 若为 0x14，恢复原始版数值；若为 0x10，保留 MCP 版（并与 `UEWrappers::GetNumElements()` 范围校验对齐）。

### P1-4：pubgmhd Profile 的 FNamePool 判定（`PUBGMHD.hpp`）

- 将 `IsUsingFNamePool()` 改为按实际布局返回，或让 AutoFix 在 FNamePool 命中时覆盖 Profile 的 false 判定。

### P1-5：LetsGo 重启稳定性

- 保持 `APPLY_PROBE_OVERRIDES` 手动 override 工作流作为兜底；自动探测鲁棒性为长期课题。
