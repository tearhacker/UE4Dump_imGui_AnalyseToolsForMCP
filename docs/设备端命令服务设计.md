> **定位**：路线图 **Phase 1（Walking Skeleton）** 的设备端落地设计。这是整条链路的**服务端**。
> 协议见 **`docs/mcp-protocol.md`**（两端唯一对齐事实，本设计是其设备端实现）。
> 上游依据：《开发必读架构 v1.2》§5.6、§4.1、§2.1；《设备端API接口清单》L0/L5；`docs/api/12-executable`（会话层精读）。

## 0. 为什么它必须先做

> 🔴 **设计前提（永久约束，非 v1 临时限制）**：
> 本项目是**单对单**——一个 PC 客户端 ↔ 一个设备端服务端，**只有一个手机在调试**，
> **不可能多客户端并发**。
>
> 由此推出：**「单连接严格串行」是最优设计，不是折中。** 并发数恒为 1，
> 为不存在的并发预留连接池 / `reqId` / 二进制协议，属于过度设计。

| 角色 | 端 | socket 动作 |
|---|---|---|
| **服务端** | 设备端 UMT | `bind("127.0.0.1",35515)` → `listen` → `accept` |
| 客户端 | PC `mcp_server` | `connect` |

**源码现状**（`docs/api/12-executable` 精读确认）：
- `src/mcp/CommandServer.cpp` 已完整实现（`:297-350`：`bind/listen/accept`）
- `main()`（`:1761`）初始化完 Vulkan 后进 `while(flag)` 渲染循环，`CommandServer` 在独立线程运行

→ **没有服务端，PC 侧 `connect` 必然 `ECONNREFUSED`。**

## 1. 线程模型（🔴 核心决策：一条线程模型都不改）

架构 §4.1 明确要求：**复用现有线程模型，不改变它**。原因是 UMT 的全部能力（L0–L7）
都依赖文件级全局（`kMgr` / `kPtrValidator` / `gDumpUiState` / `gProbeResult` / `UEWrappers`），
**全都不线程安全**。

```
┌─ CommandServer 线程（新增）────────────────┐
│  socket bind/listen/accept                 │
│  HELLO 握手（无需认证）                      │
│  NDJSON 收帧 → 入队                         │
│  NDJSON 发帧（响应/日志推送）                │
│  ⚠️ 绝不触碰任何 UMT 全局状态                │
└──────────────┬─────────────────────────────┘
               │ CommandQueue（mutex + condvar）
┌──────────────▼─ 主线程（渲染循环内 poll）───┐
│  Layout_tick_UI() 每帧 poll 一次队列         │
│  取命令 → 分级：                            │
│    ├ 快命令 → 当场执行，立即回响应           │
│    └ 重活   → 投 gWorkerThread，回 jobId     │
└─────────────────────────────────────────────┘
```

**为什么命令处理放在主线程而不是命令线程**：
所有命令最终都会调用 `kMgr` / `UEWrappers` / `gDumpUiState`，这些与 ImGui UI 操作
共享同一组全局。放在主线程执行，就与现有 UI 操作天然串行，**无需加锁改造既有代码**。

## 4. MVP 三个命令（打通 PING 即可验证全链路）

### 4.1 `PING`（快）
- **返回**：`{"build":"1.0.0","protocol":1,"connected":true}`
- **来源**：`kUEDUMPER_VERSION`（`executable.cpp:49`）+ 协议常量
- 无参数，不触碰任何 UMT 状态，**最安全的连通性验证**

### 4.2 `LIST_PROCESSES`（快）
- **参数**：`{"dedicatedOnly":false}`
- **返回**：`{"processes":[{"pid":…,"package":"…","profileName":"…","dedicated":bool}]}`
- **外迁**：`FindAutoProcessCandidates()`（`executable.cpp:166-216`）
  - 两条来源：profile `GetAppIDs()` 匹配 + 扫 `/proc` 判 maps 含 `libUE4.so`/`libUnreal.so`
  - **排序**：dedicated 优先、包名字典序
- ⚠️ 当前锁在匿名 namespace，需**移出并导出**；内部用 `KittyMemoryEx::getAllMaps`，
  不依赖 `kMgr` 已初始化

### 4.3 `GET_LOGS`（快）
- **参数**：`{"sinceIndex":0,"maxLines":50}`
- **返回**：`{"lines":[{"index":…,"level":"E","timestamp":"","message":"…"}],"totalLines":…}`
- **来源**：`gDumpUiState.logLines`（环形缓冲，`kMaxLogLines=1500`，`executable.cpp:54`/`:227-237`）
  - 格式 `"<level>: <msg>"`，取用时需解析 level 与 message
- ⚠️ **必须持 `gDumpUiState.mutex` 读取**

## 5. 命令分级（🔴 必须实现，否则 AI 会误判掉线）

协议 §7 已定。设备端落地方式：`CommandDispatcher` 持一张**快命令白名单**。

**快命令白名单**（主线程 poll 时当场执行）：
```
PING / GET_CAPABILITIES / GET_LOGS / GET_PROBE_STATUS / GET_DUMP_STATUS /
LIST_PROCESSES / LIST_OUTPUT_FILES / MEMORY_READ(size<=4096) / MEMORY_READ_VALUE /
RESOLVE_SYMBOL / READ_STRING / DECODE_ADRL / SAMPLE_GNAMES / SAMPLE_OBJECTS /
DESCRIBE_CLASS / INSPECT_OBJECT / DETECT_UE_VERSION / FOLLOW_POINTER_CHAIN /
CANCEL_JOB / END_ATTACH_SESSION
```

**其余一律投 `gWorkerThread`**（`StartProbeSelected` 等既有模式：`join()` 旧线程后起新线程，
`executable.cpp:952-954`）。

🔴 **不做分级的后果**：UMT 单 worker 线程，分钟级扫描期间 `PING`/`GET_LOGS` 全部排队
→ AI 收不到响应 → 触发重试风暴（重扫 = 又几分钟，还翻倍占资源）。

### 5.1 防卡死一：心跳帧（🔴 必需）

**问题**：命令执行期间协议是"哑等"——PC 侧无法区分设备端**在算**还是**死了**。
AI 只能盲等到超时，然后重试，而重试会让本就繁忙的设备端雪上加霜。

**方案**：设备端**独立心跳**（协议 §3.8），每 2 秒发一帧，**无论是否有请求在处理**：

```json
{"type":"heartbeat","ts":1785312000,"busy":true,"activeJobId":"j-123"}
```

| 侧 | 职责 |
|---|---|
| 设备端 | CommandServer 线程内独立计时发心跳（`busy` 反映当前是否有重活在跑） |
| PC 侧 | 超过 10 秒（≈5 个周期）无心跳 → 判定进程假死 → 断开重连 |

**心跳线程归属**：放在 **CommandServer 线程**（它不触碰 UMT 状态，只发 socket），
**不放主线程**——否则主线程被重活占满时心跳就发不出去了，恰恰失去意义。

### 5.2 防卡死二：单命令硬超时（🔴 必需）

- 每个命令设执行上限 `CMD_TIMEOUT`（默认 **120 秒**，重活可放宽但必须有上限）
- 超时 → 中断（有取消点的协作式取消）→ 回 `E_TIMEOUT` + 当前 progress
- 🔴 **绝不允许命令无限执行** —— 这是"工具调用卡死"的根因

**与取消点的关系**：worker 循环里需插协作式取消检查（架构 §4.3 `cancelRequested`），
`gWorkerThread` 的两个扫描热循环（GUObject 扫描循环、Names 分块循环）必须插检查点。

### 5.3 数据通道：大文件走 `adb pull`（🔴 不走 socket）

**NDJSON 传大文件是错的**：hex 膨胀 2 倍 + JSON 解析开销 + 撑爆响应上限。

```
设备端 dump 产物落盘 /sdcard/UnrealMemoryTools/<pkg>/
   ↓  adb pull（PC 侧直拉，绕开协议）
PC 侧本地缓存
   ↓  listOutputFiles / searchClasses / describeClass 服务端过滤
AI 只拿到它要的那一个类
```

🔴 **铁律**：几十 MB 的 `SDK_Classes.hpp` **绝不塞进协议**，也**绝不整文件读进上下文**。

## 6. 线程安全边界

| 数据 | 保护 |
|---|---|
| `gDumpUiState` | 自带 `mutex`（`:112`），**所有读写必须 lock** |
| 命令队列 | `CommandQueue` 的 mutex + condition_variable |
| `kMgr` / `kPtrValidator` / `UEWrappers` | **无锁** → 靠"命令只在主线程执行"保证串行 |
| `gProbeResult` | 同上 |

⚠️ **CommandServer 线程严禁调用任何 UMT 能力**，只做 socket I/O + 队列投递。

## 7. 安全红线

1. 🔴 **默认 `bind("127.0.0.1", 35515)`，非回环需显式放开**
   UMT 以 root 运行、提供内存读写接口。默认只监听回环；放开到非回环
   （`/sdcard/UnrealMemoryTools/mcp_bind.conf` 写入 `192.168.x.x` 或 `0.0.0.0`）
   = 局域网/蜂窝网任意设备可读写目标游戏内存，仅在可信网络下使用，用完即删配置并重启游戏。
   绑定地址在 `CommandServer::Start()` 内读取配置文件，缺省保持 `127.0.0.1`。
2. **HELLO 后直接调用**：客户端校验协议版本一致后即可发送命令，不需要 Token 或 AUTH 帧。
3. 🔴 **协议版本校验**：`protocol` 不匹配明确报错断开，不让后续命令一路失败。
4. **单连接（永久）**：只接受一个客户端（单对单是设计前提，见 §0）。
   新连接到来时**直接拒绝**（回错误后 `close()`），避免顶替现有会话状态。

| # | 验收项 |
|---|---|
| 1 | `adb shell` 下 `netstat` 可见 `127.0.0.1:35515` 处于 LISTEN |
| 2 | `adb forward tcp:35515 tcp:35515` 后，PC 侧 `nc`/Python 能连上并收到 HELLO |
| 3 | 发 `PING` 收到正确响应（`id` 配对、`ok:true`） |
| 4 | 发 `LIST_PROCESSES` 返回设备上的 UE 进程列表（元梦之星应在列） |
| 5 | 发 `GET_LOGS` 返回设备端日志（含 `[Bootstrap] …` 之类真实条目） |
| 6 | **杀掉 UMT 再重启**，PC 侧能检测到断线并按退避重连，重连后重新 HELLO 成功 |
| 7 | 不配置 Token，首条 `PING` 命令仍可直接调用成功 |

## 10. 边界：设备端**不做**什么 🔴（架构修正）

架构 §5.6.3 把 **H 组编排层**（`LOCATE_ENGINE_GLOBALS` / `DUMP_SDK` / `ANALYZE_CLASS`）
列在设备端。**经审查后修正：编排层应放 PC 侧。**

> **理由：迭代速度差两个数量级。**
> 设备端改一次 = 重新编译 NDK + `adb push` + **重启游戏**。
> 而编排逻辑（多步流程、判据组合、兜底策略）在 AI 驱动场景下会**频繁调整**——
> 今天符号优先、明天发现某游戏符号被 strip 要改走 pattern，这种调整不该每次都重编译。

**修正后的三层分工**：

| 层 | 位置 | 内容 | 变更频率 |
|---|---|---|---|
| **事实层** | 设备端 | 原语 + 已有算法（AutoFix / StructLayout / Dumper） | 低（稳定） |
| **流程层** | 🔴 **PC 侧** | 多步编排（`locateEngineGlobals` 的符号→pattern→扫描链路）、缓存、分页、格式化 | **高** |
| **判断层** | AI | 判定（工具给原始观测值，判定权在 AI） | — |

**对设备端的影响**：`Commands/HighLevel.cpp` 不再实现编排，
改为**只暴露编排所需的原子命令**（`DETECT_UE_VERSION` / `RESOLVE_SYMBOL` / `SCAN_GNAMES` / `SAMPLE_GNAMES` …），
由 PC 侧 `tools/h_highlevel.py` 组合调用。

**原则**：**设备端只给"事实"，PC 侧做"流程"，AI 做"判断"。**
